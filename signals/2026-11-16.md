# Self-Custody & Sovereignty Signal Report — Week of Nov 10 – 16, 2026

## Top 3 Signals

### 1. LDK v0.2.8 and v0.1.14 Security Releases Fix Several Funds-Loss and DoS Vulnerabilities for Nodes with Untrusted Counterparties
🔴 Strong · in-force · technical · threat, key-mgmt · [GitHub release]

**Summary:** The LDK 0.2.8 release notes say it "fixes several funds-loss vulnerabilities for nodes with untrusted counterparties", along with a fee-overpayment bug when paying static BOLT 12 invoices and several DoS bugs for nodes acting as an LSPS2 service; one fix means "a malicious counterparty can no longer cause LDK to sign differing commitment transactions at the same index". The 0.1.14 backport, also dated November 10, 2026, fixes funds-loss and DoS issues including a counterparty causing LDK to fail to claim a forwarded HTLC on a force-closed channel. Optech #431 reports both releases.
**Filter:** These bugs let a channel counterparty threaten funds held under the operator's own Lightning keys, so self-run Lightning custody depends on the operator applying these releases.
**Source:** [GitHub release] https://github.com/lightningdevkit/rust-lightning/releases/tag/v0.2.8 · 2026-11-10
**Also:** https://github.com/lightningdevkit/rust-lightning/releases/tag/v0.1.14 · https://bitcoinops.org/en/newsletters/2026/11/13/

### 2. Draft BIPs Propose a Standard Anti-Exfil Signing Protocol So a Compromised Signing Device Cannot Leak Its Seed Through Nonces (Optech #431)
🟡 Weak · early · technical · hardware, key-mgmt · [Protocol blog]

**Summary:** Optech #431 reports that Connor Avila proposed two draft BIPs to standardize exfiltration-resistant signing: a two-round protocol for Schnorr and ECDSA in which the host contributes to the nonce, and three per-input PSBT fields. Optech notes that "a compromised device may be able to leak its seed" because the device chooses the nonce, and that the work "had not received any audit on the cryptography".
**Filter:** The host could check that a signing device did not hide its seed in its signatures, so trust in the device would no longer rest only on its firmware.
**Source:** [Protocol blog] https://bitcoinops.org/en/newsletters/2026/11/13/ · 2026-11-13
**Also:** https://groups.google.com/g/bitcoindev/c/cB37_jChkEI/m/3paRGQ_IBgAJ

### 3. Draft ERC-8499 Derives Hash-Based Post-Quantum (SLH-DSA) Keys from an Existing BIP-39 Phrase
🟡 Weak · early · standards · key-mgmt, post-quantum, recovery · [EIP]

**Summary:** ERCs PR #2172, "Add ERC: Hash-Based Key Derivation from BIP-39", assigned number 8499, proposes deriving hash-based post-quantum keys from a BIP-39 phrase using hash functions only: an HKDF root with salt "HBKD/v1", derivation info that includes the account number and key type, and SLH-DSA (FIPS 205) key types. A commit message in the PR notes that "a shared phrase is only as safe as the weakest wallet that held it."
**Filter:** The seed phrase users already back up would also produce their post-quantum keys, so a migration would not need a new backup.
**Source:** [EIP] https://github.com/ethereum/ERCs/pull/2172 · 2026-11-13

## On the radar
- **Deterministic ECDSA on secp256k1: the RFC 6979 Assumption, a Counterexample, and the State of Deployed Implementations** · 🟡 Weak · academic · key-mgmt, threat: The paper isolates the assumption RFC 6979's security rests on, constructs a PRF that leaks the signing key from a single signature plus other constructions that leak it from two signatures, and reports that 28 of 31 audited secp256k1 implementations sign deterministically without added entropy and that libsecp256k1's raw-message deviation from bits2octets before version 0.2.0 survives in NBitcoin, dcrd and btcec v2. [arXiv paper] https://arxiv.org/abs/2611.18449 · 2026-11-13
- **Draft BIP Proposes One Transport-Neutral Message Encoding Between Wallet Coordinators and External Signers** · 🟡 Weak · technical · key-mgmt: A bitcoindev post by pyth and bitcoin/bips PR #2353 by pythcoiner, "BIP draft: Signing message encoding", define a byte encoding for messages between a coordinator and an external signer, such as getting xpubs, registering descriptors, verifying addresses and signing PSBTs; the post says the draft targets any external signer and whatever carries the bytes (QR, USB, NFC, a file), and covers descriptors and miniscript, BIP-388 wallet policies, MuSig2 (BIP-373) and silent payment sends (BIP-375). [Protocol blog] https://groups.google.com/g/bitcoindev/c/gmHOr6JRJyU · 2026-11-12
- **Draft ERC-7730 Update Makes the Display Order of Array Fields in Clear Signing Explicit (ERCs PR #2165)** · 🟡 Weak · standards · ux, key-mgmt: The draft PR by kuzdogan makes `iteration` required when a group has two or more array fields and makes `bundled` the default when the key is absent, and groups with fewer than two array paths stay valid without it; it notes that one library (llbartekll/clear-signing) displays `sequential` groups in a different order from the spec. [EIP] https://github.com/ethereum/ERCs/pull/2165 · 2026-11-11
- **HIT: Single-Pass Inference for Single-Trace NTT Side-Channel Attacks** · 🟡 Weak · academic · post-quantum, hardware, threat: The paper targets the NTT in ML-KEM and ML-DSA and reports running over 900x faster than prior attacks on ML-KEM-768, the first single-trace analytical attack on the ML-DSA NTT, and over 98% polynomial recovery on physical ARM Cortex-M4 targets with 20 to 80 profiling traces. [IACR paper] https://eprint.iacr.org/2026/2865 · 2026-11-11
